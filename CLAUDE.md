## dekimasen.app (concert-reminder)

Discord bot + web app tracking Japanese concert deadlines (lottery rounds,
serial-code sales, stream tickets). One Python process runs three things on a
single asyncio loop: discord.py bot, FastAPI web (Jinja2 + htmx), and a 60s
scheduler tick. SQLite + SQLAlchemy async + Alembic, gettext i18n (en/zh/ja).
Live at dekimasen.app (AWS Lightsail behind Cloudflare). ~1000+ tests.
Feature history: README.md roadmap + `WISHLIST.md`'s Shipped section — don't
propose features without checking both.

## Commands

- Run everything: `uv run python -m app.main` (dev: leave `DISCORD_TOKEN`
  empty in `.env` → web-only mode, bot and scheduler DMs disabled)
- Bot dev: set `DEV_GUILD_ID` to your test server's ID (guild slash-command
  sync in seconds; unset = production's slow global sync)
- Tests: `uv run pytest -q` — MUST pass before any commit
- Single test: `uv run pytest tests/test_service.py::test_name -q`
- Lint: `uv run ruff check .` — MUST be clean before any commit
- New migration: `uv run alembic revision --autogenerate -m "msg"` — then
  follow the migration ritual in the skill's `references/migrations.md`
  (hand-edits are REQUIRED; a raw autogenerated revision is never correct)
- Translatable strings changed: follow the catalogue ritual in the skill's
  `references/i18n.md` (both `.po` files, by hand, no fuzzy entries)
- CI (`.github/workflows/ci.yml`): `uv sync`, `ruff check .`, `pytest -q` on
  every push/PR to `main` — the same two gates as above, nothing extra.

## Layout (short map — full version: skill `references/architecture.md`)

- `src/app/domain/` — pure logic, NO I/O, no discord/fastapi/sqlalchemy
  imports (reminder math, JST↔UTC, ramen.events parsing, exports, URL guards)
- `src/app/db/` — models, session, `service.py` (ALL business logic that
  touches the DB; discord-free so it's testable)
- `src/app/bot/` — thin shell: cogs, embed builders, persistent buttons
- `src/app/web/` — thin shell: routes, templates, static (htmx UI, OAuth)
- `src/app/scheduler/` — the 60s tick that delivers DMs
- `src/app/i18n.py` — gettext plumbing (skill `references/i18n.md`)
- `tests/` — pytest; domain logic tested hardest
- `docs/superpowers/` — design specs + plans (committed before code for
  substantial features) and the concept demos that are the UI's design
  source of truth
- `WISHLIST.md` — impact-ranked feature list; read before any roadmap
  discussion, revise fully after every ship (skill `references/workflows.md`)
- Bot and web NEVER contain business logic; they call `db/service.py`.

## Non-negotiable invariants (one-liners — FULL TEXT, which you must read
before touching these areas: skill `references/invariants.md`)

1. **Timezones**: DB stores aware UTC only; forms accept JST; display is
   dual. All conversion via `domain/timezones.py`.
2. **Queue sync**: `reminder_queue` is a materialized outbox — every edit to
   concerts/windows/days/rules calls the relevant `sync_*`; only successful
   DM delivery marks a row sent; cancelled days are flagged, never deleted.
3. **Group tag expansion**: attaching a GROUP tag materializes members at
   that moment only; prunes stick; membership edits never rewrite concerts.
4. **Notifications**: system-initiated DMs go through the `notifications`
   outbox, never directly from web routes (one documented exception:
   `/me/test-dm`).
5. **Auth**: admin/editor/user tiers; DB-backed revocable sessions; signed
   out is a redirect, not an error; `?next=` hardened via `safe_next`; no
   CSRF token by design (SameSite=Lax).
6. **`event_id` vs `id`**: FKs target `Concert.id`; URLs use `event_id`
   (`"new"`/`"import"` reserved).
7. **Injection boundaries**: editor URLs through `form_url`/`clean_url`;
   inline-script data via `| tojson` on raw Python objects; user text never
   interpolated into `on*` handlers — `data-` attributes instead.
8. **Concert subscriptions are overrides, not records**: tracking is derived
   in `tracked_concert_ids` only; no row is the common case; every
   subscription/opt-out write re-syncs via `reinstate_user_rules`.

## Migrations, testing, UI

Each has hard-won rules that have bitten before — SQLite batch-mode naming
conventions and a legacy live DB the test suite structurally cannot see
(migrations), required fixtures and render tests (testing), the design-token
layer, dual-time formats, and the mobile retrofit's single-@media rule (UI).
Read the skill's `references/migrations.md`, `references/testing.md`, and
`references/ui-conventions.md` respectively BEFORE working in those areas —
the summaries here are deliberately too thin to code from.
