# Multi-language support (English / Mandarin / Japanese) — design

Date: 2026-07-20
Status: approved for planning

## Goal

Make dekimasen.app usable in English, Mandarin (`zh`), and Japanese (`ja`):
every piece of app-authored copy on the web and in Discord DMs renders in the
viewer's language, dates render in locale-correct patterns, and editors can
supply per-language variants of the user-entered text that catalogues cannot
cover (concert titles, notes, free-text venue, tag names). English remains
the source language and the default.

## Decisions (settled in brainstorming)

| Question | Decision |
|---|---|
| Surface scope | Web AND Discord together in this release |
| Anonymous visitors | `Accept-Language` auto-detect, cookie override via header switcher; cookie seeds the stored preference at first sign-in |
| Date rendering | Per-locale patterns (EN `Sat 1 Aug`, JA `8月1日(土)`, ZH `8月1日（六）`), hand-built tables, no new date dependency |
| Translation sourcing | Claude drafts all JA/ZH copy; owner reviews; catalogue files are plain text and easy to patch post-ship |
| Legal pages | Fully translated, plus an "English version governs" note in JA/ZH only |
| Catalogue mechanism | Babel + gettext (`.po`), `jinja2.ext.i18n` — chosen over a hand-rolled catalogue for its extraction tooling and translator-ecosystem compatibility |
| User-entered text | Parallel columns extending the existing `title`/`title_en` pattern |

## Architecture

New module `src/app/i18n.py` — top-level, not `domain/` (it does file I/O at
startup) and not `web/` (the bot imports it too).

- **Catalogue loading**: at startup, read `src/app/translations/{ja,zh}/`
  `LC_MESSAGES/messages.po` with `babel.messages.pofile.read_po`, compile
  in memory (`write_mo` to a `BytesIO`, construct `babel.support.
  Translations` from it). No `.mo` files on disk, no compile step added to
  the deploy ritual — `git pull && uv sync && alembic upgrade head &&
  restart` is unchanged.
- **English is the identity**: `en` maps to `NullTranslations`. Default-
  locale output stays byte-identical to today, so the existing exact-
  substring render tests pass untouched.
- **Active locale**: a `ContextVar("active_locale", default="en")`. Safe on
  the single asyncio loop. Web middleware sets it per request; the
  scheduler and bot set it per recipient before building each message.
- **Supported set**: `{"en", "zh", "ja"}`. Unknown values fall back to
  `en`. A msgid missing from a catalogue falls back to the English source
  string (gettext's native behavior) — degraded, never broken.
- **Exposed helpers**: `_()` (gettext), `ngettext()`, `get_locale()`,
  `set_locale()`, and `N_()` (no-op extraction marker for module-level
  dicts).

### Locale resolution

Web, per request (middleware in `web/app.py`):

1. `lang` cookie (set by the header switcher, and synced from
   `User.language` at every login) — the cookie is a per-browser cache of
   the stored preference, which satisfies "signed in → `User.language`"
   without a DB read in middleware. Discord always reads the column.
2. No valid cookie → parse `Accept-Language`; any `zh-*` → `zh`, `ja` →
   `ja`, else `en`.
4. OAuth callback: at user creation only, a `lang` cookie (if present
   and valid) seeds `User.language`. Existing users are never reseeded —
   the column cannot distinguish "default en" from "chose en", so only
   the moment before the row exists is safe to auto-fill. Same handoff
   shape as `tz_auto`.

Discord: each DM/interaction resolves the recipient's `User.language`
(missing row → `en`) and sets the ContextVar before calling the builders
in `bot/messages.py`. The scheduler tick does the same per queued row.

## Preference, switcher, wizard

- **Schema**: one migration adds `users.language` (`String(8)`, non-null,
  default + server_default `"en"`). No `lang_auto` companion — language is
  a one-time explicit choice; the auto-detect need is covered by
  `Accept-Language` before any stored value exists.
- **Route**: one public `POST /language` (in `web/app.py`, optional
  user via `current_user`) — validate against the supported set (422
  otherwise), always set the `lang` cookie (so sign-out keeps the
  language), additionally write `User.language` when signed in, redirect
  to a local-path-guarded `next`. One write path serving both the
  signed-in and signed-out switcher.
- **Header switcher**: the demo's 🌐 control (`EN / 中文 / 日本語`) becomes
  real in `base.html`'s right header cluster, next to the theme toggle, on
  every page including signed-out. A small native menu (not the demo's
  cycle-on-click — with three options, one click to any language beats
  cycling): a `<details>` or `<dialog>` listing all three with the current
  one marked, each option a real `<form method="post">` submit so it
  degrades without JS. Styled against both themes.
- **Preferences page**: a Language row joins the Time section (renamed
  "Time & language"), same select-and-save pattern as timezone.
- **Welcome wizard**: the timezone step gains the language select. The
  `Accept-Language`-seeded default is usually already correct, so most
  users confirm with zero extra clicks.
- **`<html lang>`**: `base.html` stamps the active locale.

## Catalogues and extraction

- **Dependency**: `babel>=2.14` in main dependencies (runtime `.po`
  loading; pure Python).
- **`babel.cfg`** at repo root, ASCII-only (GBK rule): maps
  `[python: src/app/**.py]` and `[jinja2: src/app/web/templates/**.html]`.
- **Workflow**: `uv run pybabel extract -F babel.cfg -o messages.pot src`
  → `pybabel update` into the two `.po` files → fill translations. Only
  `.po` files are committed. `messages.pot` is a build artifact
  (gitignored).
- **Templates**: add `jinja2.ext.i18n` (newstyle callables reading the
  ContextVar) to the single shared Jinja env in `web/app.py`. Short
  strings become `{{ _("Up next") }}`; interpolated or block copy uses
  `{% trans %}`. All 28 templates convert in one systematic pass.
- **Python label dicts** (`LABEL_BY_ROUND_KIND`, `LABEL_BY_ANCHOR` in
  `db/service.py`; `ANCHOR_VERB` in `bot/messages.py`): module-level, so
  they keep plain English values marked with `N_()` for extraction; the
  accessor seams (`round_kind_label` / `deadline_label` Jinja globals,
  the `ANCHOR_VERB` lookup sites, the service prose that reuses the
  labels) call `_()` at render time. No lazy-proxy machinery. The
  `LABEL_BY_ANCHOR` vs `ANCHOR_VERB` wording split ("event" vs "starts")
  is deliberate and stays; both extract.
- **Plurals**: `relative_phrase`'s hand-rolled English pluralization moves
  to `ngettext`. The JA/ZH catalogues declare `nplurals=1`.
- **Discord copy**: embed builders, button labels, cog/ephemeral replies,
  and the test-DM body all go through `_()` under the recipient's locale.
  Persistent views are constructed per-send (reminder embeds), so labels
  localize naturally; any view constructed once at startup must not bake
  in a locale — flagged for the implementation plan.

## Dates

The three formatters in `domain/timezones.py` gain an explicit
`locale: str = "en"` parameter — `domain/` stays pure (no ContextVar
import). Hand-built per-locale weekday/month tables, in the same
Windows-portable spirit as the existing hand-built day number:

- `fmt_dual_lines`: EN `Sat 1 Aug` / JA `8月1日(土)` / ZH `8月1日（六）`;
  the time line stays numeric (`19:00 JST · 07:00 ADT`) in all locales.
- `fmt_day_month`: EN `12 Oct` / JA `10月12日` / ZH `10月12日`.
- `fmt_dual`: the date part is already ISO-numeric; the weekday token
  localizes (JA `2026-08-01(土) 19:00 JST (07:00 ADT)`).

The Jinja-global registrations in `web/app.py` and the call sites in
`bot/messages.py` wrap the formatters with the active locale.

## User-entered text (parallel columns)

Catalogues cannot cover editor-entered text, so it gets per-language
columns, extending the existing `title`/`title_en` precedent.

- **Schema** (one migration, all nullable, no backfill):
  - `concerts`: `title_zh`, `notes_en`, `notes_zh`, `venue_en`, `venue_zh`
    (joining the existing `title_en`).
  - `tags`: `name_en`, `name_zh` — NOT unique; only the original `name`
    keeps its uniqueness constraint.
- **Display rule** — one helper, two registrations (a `loc` Jinja global
  and a service-side twin for Discord/board/search contexts): *viewer's
  locale column if filled, else the original field.* Empty string counts
  as unfilled. No cross-locale chaining (ZH never falls back to EN): the
  original is authoritative and always present, and in this domain it is
  usually kanji, which a Mandarin reader parses better than a
  romanization. JA viewers always see the original — there are no `_ja`
  columns; the original *is* the Japanese-side source.
- **Editor UI**: creation and edit forms gain the extra inputs inside the
  existing folded Details section, grouped under "English" / "中文"
  subheads. The ramen.events import stays Japanese-source only;
  translations are added post-import via edit.
- **Search**: `concert_search_text` (already the single source of truth
  for what search matches) gains the new columns and every tag-name
  variant, so a search in any language finds the concert. It also stays
  the source for `data-search` attributes, so client-side filtering
  matches too.
- **Render surfaces**: tag chips, board cards, deadline rows, Discover
  tiles, DM embeds — all render names/titles through `loc`, so Discord
  reminders show the recipient's language.

## Legal pages

`privacy.html` and `terms.html` translate fully via per-paragraph
`{% trans %}` blocks. The JA/ZH renders carry one extra line stating the
English version governs in any conflict; the EN render is unchanged.

## Testing

- Existing tests stay green untouched (EN default = identity path).
- New: locale-resolution matrix (user column vs cookie vs header
  precedence, unknown values); one rendered-page smoke test per locale
  for the five copy-heaviest pages (`welcome`, `preferences`, `home`,
  `discover`, `concert_edit`), each asserting a known JA/ZH string;
  date-formatter table tests across the three locales; `loc` fallback
  tests (filled, empty-string, missing); DM-builder tests with a
  ZH-preference user asserting translated embed labels; migration test
  (columns nullable, no backfill); switcher and `POST /me/language` /
  `POST /language` route tests (validation, cookie behavior, redirect
  safety).
- **Catalogue hygiene test**: invoke Babel's extraction in-process and
  assert every extracted msgid exists in both catalogues (or is on an
  explicit whitelist). This catches "edited an English string, orphaned
  its translations" in CI instead of relying on manual `pybabel`
  discipline.

## Rollout

One branch, sequenced so `pytest -q` stays green after each batch
(untranslated strings render English):

1. Plumbing: `i18n.py`, middleware, Babel dep, empty catalogues, the
   `language` column + routes + switcher + wizard step.
2. Template conversion in batches: `base`/`home` → wizard/setup →
   editor/tags/preferences → Discover/concert pages → legal.
3. Python-side: label-dict accessors, service prose, date formatters.
4. Discord: `messages.py`, `views.py`, cogs, scheduler locale setting.
5. UGC columns: migration, `loc` helper, editor inputs, search.
6. Translation fill: complete JA/ZH catalogues, owner review pass.

## Out of scope

- Locales beyond EN/ZH/JA (the mechanism supports adding more; the
  switcher and supported set are the only gates).
- Translating user data automatically (machine translation of titles).
- Localized number formatting (the app renders counts as plain digits).
- Right-to-left support.
- Localizing the concept demos (`docs/superpowers/demo/`) — they stay
  English reference mockups; the demo's language switcher is realized by
  this design rather than mirrored back.
