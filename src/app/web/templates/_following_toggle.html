Its own partial because POST /concerts/{event_id}/subscription swaps it back in after a toggle; keep the outer #following-toggle, that is the htmx outerHTML target. The route builds this context in ONE place (`following_toggle_context`) so the swapped-in copy cannot drift from the one GET /concerts/{event_id} rendered. Three states, one binary control: - following -> the button offers to opt out (state=opted_out). - opted out -> the button offers to follow, which CLEARS the override (state=default) and returns the concert to its tag default. - no row, no matching tag -> follow SUBSCRIBES it (state=subscribed). The `state` posted is decided here, not in the route, because only the template knows which of the three the reader is looking at. Heavy confirmation: opting out while holding a WON/PAID ticket names the specific loss before the write. It is a client-side gate only -- the form still posts and the route never requires the outcome to be gone (the ticket record survives the prune). The dialog ids interpolated into the on* handlers below are STATIC, so invariant 7 (no user text in on* handlers) holds; the only user-controlled value, the payment moment, goes through `dual()` in normal element text. #}
