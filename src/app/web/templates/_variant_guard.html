{#- The browser-side half of the all-or-nothing variant rule. A 422 in this app has no exception handler, no flash mechanism and no re-render path: the browser navigates to a raw JSON body and everything typed is gone. That was tolerable while 422s were rare. Making a forgotten translation a rejection made it the COMMON failure, on a form with dozens of fields -- so the browser has to catch it first, and the server's 422 stays only as the backstop for anything that bypasses the form. DELIBERATE DUPLICATION of domain/translations.py's `missing_variants`. The rule is six lines and the whole point is to never submit, so it is written twice on purpose -- but a change to one is a change to BOTH. domain/translations.py names this file in return; keep that pair intact. SCOPING -- the one thing that is easy to get wrong here. The check is NOT scoped to
descendants. _venue_create_dialog.html's v_* inputs live OUTSIDE the concert on purpose (they are read by hand and POSTed by fetch, so nesting them would post nine stray fields on every concert save), and a form-scoped check would silently skip them. So groups are found by marker instead: data-variant-scope on the enclosing block -- each leg row, each round row, each editor form, the venue dialog. Two legs both hold a `day_label` group; the per-row scope is what keeps them apart. data-variant-group the group key, unique within its scope. data-variant-slot ja | en | zh. `ja` is the original column -- there is no _ja variant (see i18n.loc_field). data-variant-label on the ja input: the field name for the message. data-variant-mandatory on the ja input: blank in all three is NOT the escape hatch it is for an optional field. data-variant-guard on a : opt in to blocking its submit.
